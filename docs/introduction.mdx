# BiH Patient Identification System

A hospital-grade, multi-tenant system that registers and verifies patients using contactless biometrics: fingerprint (single-finger and four-finger "hand slap") and face, captured with an ordinary smartphone camera. It tracks each patient through a full clinical visit lifecycle, from check-in to checkout.

## What it does

  <Card title="Clinical Visit Lifecycle" icon="clipboard-list">

  <Card title="Supervisor Overrides" icon="user-shield">

## Fingerprint matching: an honest evolution

The system did **not** launch with the matcher it uses today, and the current four-finger flow is still a work in progress rather than a finished feature:

1. **ORB feature descriptors** (original MVP), deactivated. Every ORB-format template was marked inactive by migration `2026_05_15_000001`; ORB and the matcher that replaced it are binary-incompatible, so all patients had to be re-enrolled.
2. **SourceAFIS minutiae matching** (current default, single-finger) is the production matcher for `/fingerprint/register`, `/fingerprint/verify`, and the legacy hospital-wide `POST /api/verify`. It holds up on the smartphone-camera "contact-like" captures it was tuned for.
3. **Contactless finger-photo matching is a much harder problem than contact matching.** Minutiae matching on true contactless (in-air) finger photos measured **42-50% EER** in this project's own testing, barely better than a coin flip, matching the published RidgeBase finding (CL2CL EER around 46%, even VeriFinger caps around 20%).
4. **Learned embedding matcher (Ridgeformer, ONNX)** fixes the contactless case: a deep network maps a finger photo to an embedding vector, and identity is decided by cosine similarity. Reproduced on this project's own data at **6-8% EER**, and wired into the Python service as `EmbeddingMatcher`, routed by capture domain (`contact` uses minutiae, `contactless` uses embedding when the model file is installed).
5. **Four-finger ("hand slap") capture plus fusion** is the current frontier. `POST /api/verify/hand` segments one hand photo into four fingers, matches each against enrolled hands, and fuses the scores. It is **advisory only today** (`needs_review`, never auto-accepts) because a calibrated contactless threshold for the fused score isn't installed yet. See [Architecture](/architecture#fingerprint-matching-evolution) for the full detail.

Because a single contactless matcher isn't yet a reliable stand-alone identifier at hospital scale, the recommended hospital-wide identification path is **multimodal**: a face-FAISS shortlist narrows the candidate pool, then a fingerprint match confirms one candidate. See [Verification](/api-reference/verification).

## National patient identity direction

The system was originally hospital-partitioned: a patient belonged to exactly one hospital. **ADR-013** (accepted 2026-07-10) moves the target model to a **national patient identity**, OpenHIE Client Registry/MPI-style: one patient record nationally, clinical activity (visits, stages) still owned by the hospital that produced it, and a separate audited access-control layer (`access_restricted` status, never a silent `no_match`) deciding what a given hospital's staff may see. The `patients` table already carries this direction in its schema: `jmbg` was renamed to `nida` and a `patient_identifier`/`hospital_patient_id` scheme was added. See [Architecture](/architecture#national-patient-identity) and the [ADR](/adr/national-patient-identity) for the full decision record.

## Key design principles

- **Functionality first.** MVP features before optimization or polish.
- **Honesty about accuracy.** The docs describe matcher limitations (EER numbers, placeholder/advisory states) rather than overstating what is calibrated and production-ready.
- **Security.** Raw fingerprint and face images are never persisted; only processed templates are stored, encrypted at rest.
- **Demonstrability.** Every component runs locally and is independently testable.
