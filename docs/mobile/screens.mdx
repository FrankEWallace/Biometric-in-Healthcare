# Screens reference

## SplashScreen

On launch, reads the stored Sanctum token from `SharedPreferences`. If valid, navigates to `HomeDashboard`; otherwise navigates to `LoginScreen`.

---

## LoginScreen

**File:** `lib/screens/login_screen.dart`

Accepts username + password and calls `POST /api/auth/login`. On success, stores the token and navigates to `HomeDashboard`.

---

## HomeDashboard

**File:** `lib/screens/home_dashboard.dart`

Entry point after login. Shows role-appropriate action cards. Displays the logged-in user's name and hospital.

---

## VerificationScreen

**File:** `lib/screens/verification_screen.dart`

Allows a nurse to verify a patient by:
1. Entering or scanning a patient ID
2. Triggering `FingerprintLivenessCameraScreen`
3. Submitting to `POST /api/fingerprint/verify` (known patient); the hospital-wide identification path described below is a separate flow
4. Navigating to `ResultScreen`

---

## Multimodal / hand verification screens

**Files:** `lib/screens/verify/multimodal_verification_screen.dart`, hand-capture screens under `lib/screens/`

The recommended hospital-wide identification flow when the patient isn't already known: capture a face photo and a hand photo, submit to `POST /api/verify/multimodal`. Results can be `matched`, `needs_review` (staff must confirm), `no_match`, or `access_restricted` (see [Verification](/api-reference/verification)). A dedicated four-finger-only flow (`POST /api/verify/hand`) is also available for stage verification and clerk check-in/checkout scans; it currently always returns `needs_review`. See [Architecture: fingerprint matching evolution](/architecture#fingerprint-matching-evolution).

---

## FingerprintPreviewScreen

**File:** `lib/screens/fingerprint_preview_screen.dart`

Displays the captured image. Allows the user to:
- **Retake**: go back to `FingerprintLivenessCameraScreen`
- **Confirm**: upload the image to the appropriate API endpoint

---

## ResultScreen

**File:** `lib/screens/result_screen.dart`

Displays the verification verdict:

| Verdict | Display |
|---|---|
| MATCH | Green card with patient name, EHR summary, insurance status |
| NO MATCH | Red card with failure message |
| LOCKED | Orange card with lock message and admin contact info |

---

## PatientRegistrationScreen

**File:** `lib/screens/patient_registration_screen.dart`

Form for registering a new patient. Fields:

- Full name (required)
- Date of birth (required)
- Gender
- NIDA (national ID, 20 chars, renamed from the earlier "JMBG" field; see [Architecture: national patient identity](/architecture#national-patient-identity))
- Phone
- Notes

Submits to `POST /api/patients`. On success, optionally proceeds to fingerprint enrollment.

---

## Clerk screens

**Files:** `lib/screens/clerk/patient_search_screen.dart`, `clerk_scan_screen.dart`, `fingerprint_enroll_screen.dart`

Clerk-role screens supporting the visit lifecycle:

- `PatientSearchScreen`: find a patient by name, hospital patient ID, or phone (`GET /api/visits/patient-search`); also doubles as the entry point for the Retake Fingerprints flow (`retakeMode: true`) from the nurse dashboard.
- `ClerkScanScreen`: biometric scan feeding `POST /api/visits` (open) or `PUT /api/visits/{visit}/close` (close), and check-in/check-out stage verification.
- `FingerprintEnrollScreen`: used for both first enrollment and, with `isRetake: true`, replacing an existing patient's fingerprints.

---

## EHRScreen

**File:** `lib/screens/ehr_screen.dart`

Displays the patient's Electronic Health Record (EHR) data fetched from the GoT-HoMIS integration. Read-only. Accessible to nurses and doctors.

---

## EditRequestScreen

**File:** `lib/screens/edit_request_screen.dart`

Allows nurses to submit demographic edit requests for existing patients, one field at a time (`field_name`, `new_value`, `reason`); see [Edit Requests](/api-reference/edit-requests). Admin reviews and approves/rejects via the web dashboard.
