## Request flow: hospital-wide multimodal identification

```
Nurse opens the "Identify unknown patient" screen
        │
        ▼
Flutter captures a face photo + a hand photo
        │
        ▼
POST /api/verify/multimodal (face_image + fingerprint_image base64)
  Authorization: Bearer <sanctum-token>
        │
        ▼
Laravel: geofence check, then
  1. Face liveness check (moiré + specular-highlight heuristics)
  2. Face embedding → FAISS top-5 shortlist (national gallery, hospital-agnostic)
  3. Hand photo segmented into 4 fingers → contactless matcher scored ONLY
     against the shortlisted patients' hands (1:few, not 1:N)
  4. Decision:
       matched           — fingerprint confirms a shortlisted candidate
       needs_review       — face found candidates, fingerprint could not confirm
       no_match            — face produced no usable candidates
       access_restricted   — identity resolved, but the caller's hospital has
                             no authorized relationship to this patient
        │
        ▼
JSON response → Flutter shows result / manual-review / access-denied screen
```

<Note>
  The legacy `POST /api/verify` (1:N fingerprint-only hospital-wide scan) still exists for backward compatibility but is **deprecated**. It emits RFC-8594 `Deprecation`/`Link`/`Warning` headers pointing at `/api/verify/multimodal`. Its false-accept risk grows with the number of enrolled patients because it searches every active fingerprint at the hospital; the multimodal flow bounds that risk with a small face shortlist. See [Verification](/api-reference/verification).
</Note>

## Fingerprint matching evolution

This is worth stating plainly rather than glossing over, because the accuracy story is a core part of this project's engineering record:

| Stage | What it was | Status |
|---|---|---|
| ORB feature descriptors | Classic OpenCV keypoint/descriptor matching (the original MVP) | **Deactivated.** Migration `2026_05_15_000001` marks every ORB-format template `is_active = false`. ORB and SourceAFIS templates are binary-incompatible, so affected patients had to be re-enrolled. |
| SourceAFIS minutiae matching | Crossing-number minutiae extraction + SourceAFIS-style matching, tuned on smartphone camera captures | **Production default** for single-finger enrollment/verification (`/fingerprint/register`, `/fingerprint/verify`, legacy `/api/verify`). Registered as the `contact`-domain `Matcher`. |
| Minutiae on true contactless photos | Same minutiae approach applied to in-air finger photos | **Fails.** Measured **42-50% EER** on this project's own contactless test data, consistent with the published RidgeBase CL2CL finding (~46% EER; even commercial VeriFinger caps ~20% on this domain). Minutiae is non-discriminative on finger photos; it is not a calibration problem, it's a representation mismatch. |
| Learned contactless embedding matcher | A Ridgeformer-style deep network exported to ONNX, served via `onnxruntime`, scored by cosine similarity | **The fix.** Reproduced on this project's own data at **6-8% EER**. Wired into the Python service as `EmbeddingMatcher` (`python-service/app/services/embedding_service.py`), routed by domain: `get_matcher("contactless")` returns it once `models/contactless_embedding.onnx` (~1.1GB, gitignored) is present, and falls back to the minutiae matcher otherwise so the pipeline never crashes on a missing model. |
| Four-finger ("hand slap") fusion | One hand photo, segmented into 4 fingers, each scored, then fused (mean by default) | **Current frontier, advisory only.** `POST /api/verify/hand` and the fingerprint-confirm step of `POST /api/verify/multimodal` both use this. Until `FINGERPRINT_CONTACTLESS_MATCH_THRESHOLD` is calibrated for the fused embedding score, the endpoint **always returns `needs_review`** and never auto-accepts. It deliberately does not claim accuracy it hasn't proven yet. |

**Why not just ship the four-finger flow as fully automatic?** Fusing scores with the *minutiae* matcher only brings four-finger EER down to ~42% (√N noise reduction on an already-bad signal doesn't rescue it). The embedding matcher is the one that actually works, but the fused, calibrated operating threshold for it at this project's target FAR/FRR trade-off has not been finalized. The honest state to ship is "advisory," not "silently probably fine."

## Visit / stage state machine

A patient's hospital encounter is modeled as a `Visit` moving through six ordered `VisitStage`s, each owned by a specific role:

```
clerk_checkin → triage → consultation → laboratory → pharmacy → clerk_checkout
   (clerk)      (nurse)    (doctor)   (lab_technician) (pharmacist)  (clerk)
```

- A visit is **opened** by a clerk (`POST /api/visits`) after a successful biometric verification log exists for the patient, and **closed** by a clerk (`PUT /api/visits/{visit}/close`) the same way. A same-day closed visit can be **reopened** with a required reason.
- Each stage requires its assigned role to re-verify the patient's identity biometrically (`POST /api/visits/{visit}/stages/{stage}/verify`) before that stage's simulated EMR data can be submitted (`PUT .../data`). Role enforcement is **deny-by-default**: an unmapped stage name permits no role, never any role.
- Stage verification runs a tiered pipeline: four-finger hand embedding first, face as fallback; a legacy single-finger fingerprint image, if supplied, is advisory only and can never complete a stage on its own.
- Triage is the only stage that can set the visit's `visit_type` (`opd` or `ipd`) via its simulated data payload.
- When biometric verification fails or can't be attempted at a stage, staff request a **supervisor override** (`POST /api/supervisor-overrides`). A different admin/doctor/nurse than the requester must resolve it, since self-approval is explicitly forbidden (segregation of duties). An approval completes the stage without any verification log, using the stage's default simulated data.

See [Visit Lifecycle](/visit-lifecycle) for the full walkthrough and [Supervisor Overrides](/api-reference/supervisor-overrides) for the API.

## National patient identity

<Note>
  **ADR-013**, accepted 2026-07-10, is the architectural direction, not yet the shipped data model. `patients.hospital_id` still exists and is still the enforced boundary today.
</Note>

The system today is hospital-partitioned: `patients.hospital_id` scopes a patient to the hospital that enrolled them, enforced by `App\Policies\PatientPolicy` (returns 404 across hospitals). The accepted direction (see the [ADR](/adr/national-patient-identity)) is:

1. **Identity is national.** One patient record exists regardless of which hospital first registered them; biometric search (face FAISS, four-finger embedding matcher) already effectively operates over the whole gallery for face and hand verification.
2. **Clinical activity stays hospital-owned.** Visits, stages, and verification logs belong to the hospital that produced them and reference the national identity by foreign key.
3. **Access is a separate, audited decision** made *after* identity resolves, via `PatientAccessService::authorizePatientAccess(User, Patient)`. A cross-hospital hit returns `access_restricted` (identity found, records withheld, zero PII, but the resolved patient id is still written to the audit log), **never** a fake `no_match`, because that would push a nurse toward duplicate re-enrollment or an unsafe assumption of no prior history.

`patients.jmbg` was renamed to `patients.nida` (migration `2026_05_05_142209`) and `hospital_patient_id`/`patient_seq` were added (migration `2026_05_17_000002`). This is schema groundwork for this direction, ahead of the full `patient_hospital_links` migration described in the design doc.

<Warning>
  Do not read this section as "the system already enforces national identity end to end." The `hospital.access` middleware (`CheckHospitalAccess`) is an **unrelated IP/CIDR network geofence** on hospital-scoped API routes, not the patient-ownership boundary. Patient ownership is enforced in `PatientPolicy` and, for the biometric verification paths, in `PatientAccessService`. Conflating the two was an earlier framing mistake the ADR explicitly corrects.
</Warning>

## Security layers

1. **Sanctum token.** Expiry is configurable (`SANCTUM_TOKEN_EXPIRY_HOURS`, default 8h), revoked on logout, single active token per user.
2. **Role middleware.** `role:x,y` is checked before every sensitive route.
3. **Hospital network geofence.** The `hospital.access` middleware (`CheckHospitalAccess`) restricts hospital-scoped routes to each hospital's configured IP/CIDR ranges. This is a network boundary, not the patient-ownership boundary (see above).
4. **Patient ownership / access.** `PatientPolicy` (object-level, 404 across hospitals) and, for biometric identification, `PatientAccessService::authorizePatientAccess` (post-identification, audited, `access_restricted` on denial).
5. **GPS + WiFi geofence.** Flutter checks GPS + WiFi SSID before allowing capture; the backend re-validates via the `geofence` middleware, failing closed in production (`GEOFENCE_FAIL_OPEN=false`).
6. **Internal service key.** Laravel and Python calls carry a shared `X-Internal-Api-Key`, required in production.
7. **Fingerprint locking.** 5 failed attempts within 1 hour locks the record.
8. **Template encryption.** Fingerprint/face template JSON is encrypted at rest (AES-256).
9. **No raw image storage.** Only processed feature templates are persisted.

See [Security](/security) for the full model, including known weak points this FYP is honest about.
