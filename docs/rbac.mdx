# Role-Based Access Control

The system has **seven roles**, defined in `App\Models\User` and enforced by the `role:x,y` middleware on every sensitive route in `laravel/routes/api.php`. This page transcribes that file's role matrix comment block plus the actual middleware on each route group, so it stays the single source of truth alongside the code.

<Note>
  `role:x,y` middleware failures return `403`. `hospital.access` failures (wrong IP/CIDR range) also return `403` but are a network geofence, not a role check. See [Security](/security#authorization).
</Note>

## Roles at a glance

| Role | Scope | Assigned visit stage |
|---|---|---|
| `super_admin` | Cross-hospital platform management; **no** clinical data access | n/a |
| `admin` | Own-hospital management, emergency enrollment | n/a |
| `doctor` | Read-only clinical (EHR, patients, audit logs) | `consultation` |
| `nurse` | Fingerprint/face verification, patient registration, enrollment | `triage` |
| `clerk` | Visit open/close/reopen, patient search | `clerk_checkin` **and** `clerk_checkout` |
| `lab_technician` | Laboratory stage | `laboratory` |
| `pharmacist` | Pharmacy stage | `pharmacy` |

`User::assignedStage()` returns `null` for `clerk` because clerk covers **both** check-in and check-out stages, not a single stage.

### Stage-verify role mapping (enforced inside `VisitStageController`)

`POST /visits/{visit}/stages/{stage}/verify` and `PUT /visits/{visit}/stages/{stage}/data` are not gated by `role:` middleware in the route file. The controller looks up `VisitStage::STAGE_ROLES[$stageName]` and denies (403) unless the caller's role is in that list. This is **deny-by-default**: an unmapped stage name permits no role, never any role.

| Stage | Allowed role |
|---|---|
| `clerk_checkin` | `clerk` |
| `triage` | `nurse` |
| `consultation` | `doctor` |
| `laboratory` | `lab_technician` |
| `pharmacy` | `pharmacist` |
| `clerk_checkout` | `clerk` |

### Supervisor override resolution

`PUT /supervisor-overrides/{override}/resolve` allows `admin`, `doctor`, or `nurse`, but **never** the same user who created the request (`self_approval_forbidden`, HTTP 403), regardless of role. This segregation-of-duties rule is enforced in the controller, not the route middleware.
