# Facial recognition: design decisions

This page records every question asked and answer chosen when designing the facial recognition feature. Use it as a reference when extending the feature, onboarding a new developer, or revisiting a past decision.

<Note>
  The Q&A below is the original design record and its impact statements are still accurate for the pieces that haven't changed (the `face_templates` table shape, the alternative-not-multi-modal verification choice's *history*, the super-admin-only toggle, the login-payload feature flag). The **face embedding algorithm itself has since changed**. See the [Algorithm note](#algorithm-note) at the bottom, which reflects the current InsightFace (buffalo_s) + FAISS implementation, not the original Haar/LBP MVP described when this record was first written. The verification flow has also grown beyond "alternative": see [Verification](/api-reference/verification) for the current multimodal (face shortlist, then fingerprint confirm) and four-finger flows, which sit alongside the original single-modality alternative described in Q1.
</Note>

---

## Q1: verification flow, alternative or multi-modal?

**Question:** When a hospital enables facial recognition, what should happen during verification?

| Option | Description |
|---|---|
| A: Alternative ✅ | Staff choose either fingerprint or face per session. One match is enough. |
| B: Multi-modal | Patient must pass both fingerprint and face. Higher security, more friction. |
| C: Face replaces | Hospital switches entirely to face, fingerprint no longer used. |

**Chosen: A (Alternative)**

**Why:** Most practical for a clinical setting. A patient with bandaged hands can still be verified by face; a patient with a face covering can still use fingerprint. Existing fingerprint workflows are completely unaffected for hospitals that never enable facial recognition.

**Impact:** Two separate verification endpoints exist (`POST /api/verify` for fingerprint, `POST /api/face/verify` for face). The Flutter app shows both options when the feature is enabled and the patient has both templates enrolled. A single match from either modality is sufficient.

## Q2: who controls the on/off toggle?

**Question:** Which role can enable or disable facial recognition for a hospital?

| Option | Description |
|---|---|
| A: Super admin only ✅ | Platform-level control, consistent with all other hospital settings. |
| B: Super admin enables, local admin can disable | Shared control. |
| C: Local admin full control | Hospital autonomy, no super admin needed. |

**Chosen: A (Super admin only)**

**Why:** All hospital settings already live in `HospitalController`, which is fully gated behind the `super_admin` role. Adding a new flag here is consistent and keeps capability management at the platform level.

**Impact:** The toggle is a checkbox in the **Settings** tab of the hospital detail page in the admin dashboard. Only super admins see that page. The column `face_recognition_enabled` (boolean, default `false`) was added to the `hospitals` table.

## Q3: what happens to existing patients when the feature is turned on?

**Question:** A hospital has 500 enrolled patients (fingerprint only). The super admin enables facial recognition. What happens?

| Option | Description |
|---|---|
| A: Enroll on next visit ✅ | Fingerprint keeps working. Staff enroll face naturally when the patient visits. |
| B: Face unavailable until enrolled | Face option hidden per-patient until they have a template. |
| C: Block all verification | Existing patients must re-enroll before they can be verified at all. |

**Chosen: A (Enroll on next visit)**

**Why:** Least disruptive migration path. No forced re-registration, no disruption to existing operations. Face templates accumulate over time as patients visit.

**Impact:** `POST /api/face/enroll` upserts, so re-enrollment replaces the old template. The verification endpoint returns `no_match` (not an error) when a patient has no face template yet, allowing the nurse to fall back to fingerprint.

## Q4: where are face templates stored?

**Question:** Where should the face embedding data live in the database?

| Option | Description |
|---|---|
| A: New `face_templates` table ✅ | Dedicated table, mirrors the `fingerprints` pattern. |
| B: Column on `patients` | Simple but conflates identity with biometric data. |
| C: Reuse `fingerprints` with a `type` column | Avoids a new table but pollutes a clean schema. |

**Chosen: A (New `face_templates` table)**

**Why:** Face data is structurally different from fingerprint data: no finger position, no locking mechanism, one face per patient. A dedicated table keeps each biometric type independently queryable and doesn't compromise the existing fingerprint locking/quality logic.

**Impact:** `face_templates` has columns: `patient_id` (unique, one face per patient), `hospital_id` (denormalised for fast hospital-scoped queries), `enrolled_by`, `template` (AES-256 encrypted embedding JSON), `quality_score`, `is_active`. Raw embeddings are never stored unencrypted.

## Q5: where does face processing run?

**Question:** Should facial recognition be added to the existing Python service or run as a separate microservice?

| Option | Description |
|---|---|
| A: Extend existing service ✅ | New `/face/process` and `/face/match` routes in the same FastAPI app. |
| B: Separate microservice | Independent process, independent scaling. |

**Chosen: A (Extend existing service)**

**Why:** One Python process is simpler to run and deploy, especially for an FYP environment. OpenCV and NumPy are already present. The face routes live in `app/routes/face.py` and are registered in `main.py`. Splitting into a second service is straightforward later if load demands it.

**Impact:** `PYTHON_SERVICE_URL` in `.env` serves both fingerprint and face endpoints. The face router is mounted at `/face/*` so there is no collision with existing fingerprint routes.

## Q6: how does the Flutter app know the feature is enabled?

**Question:** How does the app know whether to show the face verification button?

| Option | Description |
|---|---|
| A: In the login/me response ✅ | `hospital.face_recognition_enabled` added to the auth payload. Read once on login. |
| B: Dedicated `/api/hospital/settings` endpoint | Separate call on startup. |
| C: Per-request flag | Included in every `/api/verify` response. |

**Chosen: A (In the login/me response)**

**Why:** Zero extra network calls. The app already receives user and hospital context on login. One extra boolean costs nothing and the UI can render correctly from the moment authentication completes.

**Impact:** `AuthController::userPayload()` now returns a nested `hospital` object:

```json
{
  "hospital": {
    "id": 1,
    "name": "Central Hospital",
    "face_recognition_enabled": true
  }
}
```

This is returned by both `POST /api/auth/login` and `GET /api/auth/me`.

## Q7: where in the admin UI does the toggle live?

**Question:** Where should the facial recognition toggle appear in the dashboard?

| Option | Description |
|---|---|
| A: In the existing hospital settings form ✅ | Checkbox alongside GPS radius, WiFi SSID, etc. |
| B: Separate "Features" tab on the hospital detail page | Dedicated tab for capability toggles. |

**Chosen: A (Existing settings form)**

**Why:** Only one feature flag exists. A dedicated tab would be premature. The checkbox sits in a **Feature Flags** card inside the existing settings form, easy to find, with no extra navigation.

**Impact:** The hospital settings form posts `face_recognition_enabled` as a boolean checkbox. `HospitalController::update()` reads it with `$request->boolean('face_recognition_enabled')`, which correctly treats an absent checkbox (unchecked) as `false`.

## Algorithm note

<Warning>
  The paragraph below describes the **original** MVP algorithm (Haar cascade + LBP), kept for historical accuracy of this decision record. The system has since upgraded; see "Current implementation" underneath.
</Warning>

The face embedding *originally* used **OpenCV Haar cascade + LBP grid histogram**, which needed no additional pip installs. This was intentional for the earliest MVP/FYP milestone, deliberately trading accuracy for zero new dependencies.

### Current implementation

The Python service now uses **InsightFace (`buffalo_s` model pack, ArcFace embeddings)** for `POST /face/process`, with a **FAISS** index (`faiss-cpu`) backing `POST /face/identify` for hospital-wide 1:N search. This is a real upgrade to a production-grade face recognition model, not the Haar/LBP placeholder:

- Embeddings are 512-dimensional, L2-normalizable vectors; identity is cosine similarity.
- Two thresholds are in play, calibrated to different jobs: `IDENTIFY_THRESHOLD = 0.40` (`FaceService::IDENTIFY_THRESHOLD`) is the floor used when building a 1:N shortlist (e.g. in `POST /api/verify/multimodal`), and `MATCH_THRESHOLD = 0.75` (`FaceService::MATCH_THRESHOLD`) is the stricter bar `POST /api/face/verify` uses to decide `matched` vs `no_match` outright. Both sit within the generally cited buffalo_s cosine-similarity operating band of roughly 0.30–0.45 for identification-style matching; the higher `MATCH_THRESHOLD` is a deliberately more conservative bar for a direct accept/reject decision.
- **Known limitation:** like any 1:N identification, false-accept risk scales with the number of enrolled patients (gallery size) at a fixed per-comparison threshold. See [Security](/security#1n-false-accept-risk-scales-with-gallery-size-a-known-limitation). This is the reason `POST /api/verify/multimodal` exists: face narrows the candidate pool, fingerprint confirms the specific candidate, instead of trusting a single 1:N face score at hospital scale.
- Borderline results are not auto-decided: `POST /api/face/verify-confirm` records a staff member's manual confirmation of a `needs_review` result, creating an explicit audit trail entry rather than silently accepting or rejecting a marginal score.

The Laravel layer remains algorithm-agnostic. No Laravel-side change was required for this upgrade, matching the modularity goal Q5 already designed for.
