## Dependency notes

- **002 depends on 001**: repointing the stage pipeline onto the four-finger
  embedding path needs a runnable test harness to prove the hand/embedding tier
  works rather than only through Laravel mocks.
- **002 also touches Flutter**: it changes the stage-verify contract from a single
  `fingerprint_image` to a `hand_image`, so `visit_service.dart` and
  `stage_verify_screen.dart` change alongside the Laravel service. The embedding
  matcher becomes the core (decides at threshold 57.5), face is the fallback, and
  single-finger minutiae is demoted to advisory-only (can never complete a stage).
- **011 depends on 001**: the FAISS-shortlist refactor changes scoring; it needs
  the score-parity tests that 001 makes possible.
- 003, 004, 005, 009 are independent and can run in parallel.
- 010 (docs) should run last or after 002/009 so it documents the true post-fix
  state, not a moving target.
- **016 is independent and isolated on purpose**: it's a new `web-admin/`
  Next.js app consuming the existing API, branched from `main` on its own
  `feature/016-nextjs-admin-dashboard` branch — it does not depend on, and must
  not be rebased onto, any other plan's branch. It only touches Laravel to add
  a small number of net-new, additive endpoints (geofence/device config), never
  existing biometric/verification code.
- **005 and 013 implement the same principle at two scopes.** Decided 2026-07-08
  (modified option a): identity is resolved **nationally** in the matcher NOW;
  the hospital boundary is enforced as a separate, audited **access-control step
  after** identification — returning `access_restricted` (identity found, records
  withheld), never a fake `no_match`. Plan 005 introduces that access seam for the
  face path (a named `authorizeRecordAccess` step). Plan 013 designs the fuller
  access layer that seam grows into (consent tuple, break-glass, referral policy,
  national-ID migration + dedup). The hospital-match rule lives in the access step,
  so enabling cross-hospital referrals later is a policy change, not a
  biometric-engine rewrite. Do NOT remove `hospital_id`/`hospital.access` — the
  boundary is relocated, not deleted.
- **005 covers BOTH active biometric paths together** (face verify + four-finger
  hand verify) via one shared `PatientAccessService`, so the two never diverge on
  the same person. The deprecated 1:N minutiae `verify` route is intentionally left
  hospital-scoped (being removed). Effort is L because it spans two controllers +
  Flutter + a shared service; ship it as one merge, not split.
- **Two decisions deferred to the next architecture review** (flagged 2026-07-08,
  bigger long-term impact than the 005 code): (1) whether `access_restricted` is
  exposed to clients or suppressed to `no_match` audit-only; (2) whether
  `patient->hospital_id` is the right ownership model or it becomes National Patient
  + Hospital Record. Both are recorded as decision points in plan 013.
- **014 was discovered live while implementing 002**, not from the original
  audit — `POST /api/visits` (`VisitService::openVisit`) currently fails in
  every environment (reproduced against the dev MySQL DB, not just sqlite
  tests) because `Visit::create()` tries to insert `created_at`/`updated_at`
  into a table that doesn't have those columns. This is independent of 002's
  biometric changes but sat undiscovered because no test exercised
  `VisitController::store`. Treat as P0 — run before anything else that
  depends on opening a new visit.
- **015 was deferred out of 002**: the plan asked for a widget test on the
  changed stage-verify screen, but this repo has no mock/screen-test
  infrastructure at all (one smoke test, no mocktail/mockito). 015 builds
  that infrastructure once, including the specific test 002 deferred
  (`stage_verify_screen_test.dart`), so future UI plans don't hit the same gap.

## Priority rationale

- **P0** (014) is a confirmed, currently-live break of the visit-opening
  workflow itself — nothing downstream of `POST /api/visits` can run until
  it's fixed, regardless of how correct 002's biometric logic is.
- **P1** items are either active correctness breaks (002, 005), exploitable
  boundary/authz gaps (003, 004), the verification baseline that unblocks safe
  change (001), or a one-session config-hardening win (009).
- **P2** items are real but latent races / consistency bugs (006, 007, 008) and
  doc drift (010).
- **P3** items are performance and cleanup that matter at scale, not for a pilot
  demo (011, 012, 015).

## Findings considered and rejected

- **"Python biometric service is unauthenticated"** — refuted. `INTERNAL_API_KEY`
  is set and required on all biometric routers (`python-service/app/main.py`),
  and the service is `expose`-only, never host-published (`docker-compose.yml`).
- **"Geofence/liveness trusted from client"** — refuted for the configured-perimeter
  case; server-side enforcement exists (`EnforceGeofence.php`, `GeofenceService`).
  Client-reported GPS/SSID spoofability is a documented defence-in-depth tradeoff.
- **"Raw biometric images retained"** — refuted. Only encrypted templates persist
  (`Fingerprint::setTemplate` uses `Crypt::encryptString`); temp images are unlinked.
- **"Mass assignment / IDOR"** — refuted. Controllers use explicit `validate()` and
  hospital-scoped 404s throughout.
- **"ONNX contactless matcher is scaffolded/inactive"** — stale claim. The model
  file, threshold env var, and wiring exist. The residual issue is documentation
  drift, folded into plan 010; there is no code gap to fix here.
- **"Major dependency version lag"** — none. Laravel 13 / PHP 8.3 / Sanctum 4 /
  FastAPI / onnxruntime / faiss are all current.
- **Flutter god-screen refactor (DEBT-03)** — not planned. LOW confidence
  (duplication smelled but not line-verified) and L effort; revisit only if the
  capture UX is actively reworked.
